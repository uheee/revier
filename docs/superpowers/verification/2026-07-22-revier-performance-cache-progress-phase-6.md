# Revier 性能缓存与进度改造：阶段六验收记录

## 1. 本阶段范围

本阶段交付提交下钻持久化缓存、热缓存快速路径、编码替换和提交下钻操作进度。统一状态栏剩余操作种类与最终性能汇总属于后续阶段，本阶段不扩展其他功能。

## 2. 实现结果

### 2.1 下钻缓存读取

- `review_get_commit_overlay` 请求新增 `operation_id` 和 `cache_mode`。
- 普通打开使用 `prefer-cache`，先定位当前分支快照和当前文件的 `file_analysis_id`。
- 缓存只在当前文件分析、提交哈希、算法版本和实际编码全部匹配时命中。
- 热缓存直接按旧、新 Blob ID 读取不可变 Git 对象，恢复提交块和作者信息。
- 热缓存仍校验提交对象的第一父提交哈希；缓存记录不完整或块几何不一致时按未命中重新计算。
- Blob 丢失沿用稳定 `CACHE_INVALID`，不回退到可能掩盖缓存损坏的伪结果。

### 2.2 冷路径与原子发布

- 未命中时保留原有提交可达性、历史路径、第一父提交和提交文件差异逻辑。
- 计算成功后保存历史路径、第一父提交、两侧 Blob ID、实际编码、块几何、算法版本和耗时。
- 下钻缓存通过事务原子替换；失败不会删除原记录。
- 同一文件分析下，不同提交分别保存。
- 同一提交切换编码后只保留当前编码版本，避免缓存膨胀。
- 当前文件重新分析成功后，既有仓储逻辑会删除该文件全部旧下钻缓存；失败时保持不变。

### 2.3 前端与进度

- 打开提交和按编码重载提交都会创建独立操作 ID。
- 状态栏显示当前文件、提交哈希、加载状态、缓存状态和连续耗时。
- 后端缓存命中时终态消息为“已从缓存加载提交”。
- 关闭下钻后再次点击同一提交仍请求后端，由 DuckDB 热缓存恢复，不依赖页面内存缓存。
- 旧请求代次保护、失败通知和关闭清理语义保持不变。

## 3. 缓存有效性与空间

- 下钻必须属于当前 `file_analysis_id`，不会跨项目快照或文件分析复用。
- 每个 `file_analysis_id + commit_hash` 只有一条下钻记录。
- 源码正文不写入数据库，只保存 Blob ID 和紧凑块坐标。
- 提交与 Blob 由不可变对象 ID 定位；热缓存不重新执行范围可达性、路径连接和提交树差异扫描。
- 旧式索引数据库没有缓存表时保持原冷路径行为，不让可选缓存影响提交下钻正确性。

## 4. 测试覆盖

- 首次点击写入历史路径、Blob ID 和提交块。
- 第二次点击返回 `hit`，且结果与冷路径一致。
- 破坏任务范围 HEAD 后热缓存仍可打开，证明未重新解析范围历史。
- 不同提交形成两条独立缓存记录。
- 同一提交切换编码返回未命中并原子替换，记录数保持不变。
- 当前文件刷新成功清除旧下钻、失败保留旧下钻由仓储测试持续覆盖。
- 新增、删除、重命名、UTF-16、二进制、根提交、不可达提交和多次重命名历史测试继续通过。
- 提交操作事件包含正确的操作类型、提交哈希、缓存状态和连续耗时。
- 前端关闭后再次打开、缓存命中终态和请求契约测试通过。

## 5. 性能记录

在本阶段线性 Git 夹具与未优化测试构建中：

| 场景 | 本次耗时 |
| --- | ---: |
| 首次提交下钻计算并写入缓存 | 174 ms |
| 同提交、同编码热缓存恢复 | 87 ms |

该结果只验证冷热路径分流，不代表大型仓库的绝对耗时。热缓存仍需从 Git 对象库读取源码，但后端直接恢复缓存块，不再生成行差异，也不会重新扫描提交可达性、历史路径或提交树差异。
