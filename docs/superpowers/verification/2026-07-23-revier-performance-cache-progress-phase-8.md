# Revier 性能缓存与进度改造：阶段八最终验收记录

## 1. 验收范围

本阶段执行性能矩阵、正确性全回归和文档收尾。测试环境为 Windows、Rust debug 测试构建与本机 Node 24/pnpm 环境；性能数字为单次诊断样本，用于确认冷热路径分流，不是发布构建基准。

## 2. 小型 fixture 性能矩阵

| 场景 | 冷路径 | 热路径／刷新 | 结果 |
| --- | ---: | ---: | --- |
| 首次项目分析 | 452 ms | 不适用 | 完成并发布分支快照 |
| 新增一个提交后刷新 | 不适用 | 379 ms | 只增量写入缺失提交并替换快照 |
| 再次打开分支 | 不适用 | 65 ms | 从 DuckDB 恢复任务、文件和最后选择 |
| 文件归因 | 257 ms | 115 ms | 同编码、同块签名热缓存命中 |
| 当前文件强制刷新 | 不适用 | 268 ms | 重算并原子替换文件分析 |
| 提交下钻 | 166 ms | 83 ms | 同文件分析、提交和编码热缓存命中 |

热缓存相对冷路径：文件归因约减少 55%，提交下钻约减少 50%。fixture 的两分支紧凑缓存共有 2 个快照、2 组作者、2 组 Glob 和 2 个文件记录，DuckDB 落盘 3,944,448 字节；该大小包含 DuckDB 固定页开销，不能线性外推到大型仓库。

## 3. 当前仓库诊断

测试范围为 `develop`，HEAD `1d9e877051be31ec27cfc92dd92b15583797565e`：

| 场景 | 结果 |
| --- | ---: |
| 首次索引 183 个提交、1100 条文件记录 | 3,230 ms |
| 无新增提交再次索引 | 220 ms |
| 最近 50 个提交计算 130 个最终变化文件 | 2,541 ms |
| 相同范围重复计算 | 2,573 ms |
| 隔离索引数据库大小 | 4,993,024 字节 |

重复“范围文件计算”是显式重新分析路径，会重新计算最终文件统计，因此不应解释为分支热缓存。正常再次打开项目走分支快照恢复，不执行该查询。

对 4,766 行、最近范围内净增 3,320 行的 `src-tauri/src/services/review.rs` 执行旧 CLI 一体化 Overlay/归因，120 秒内未完成。桌面应用已把文件内容读取、Monaco Diff 和目标块归因拆开并缓存，但超大变更文件的首次归因仍可能很慢；这是本次验收确认的已知限制。第二次打开在规范块签名一致时走持久化归因缓存。

## 5. 数据库迁移结论

- 当前 schema v3；不同分支分别保存一个最近成功快照。
- v1 → v2 创建规范化缓存表，v2 → v3 增加最后选中文件。
- 迁移在事务中完成，失败回滚且保留原版本。
- 文件与提交缓存不保存源码正文，只保存 Blob ID、块坐标和归因关系。
- 详细说明见 `docs/cache-schema.md`。

## 6. 已知限制与建议

- 超大文件或大范围净变化的首次归因仍受 patch inference、blame 和删除追踪成本影响，可能超过 120 秒；后续命中缓存可避免重复计算。
- Monaco 计算发生在 WebView，当前自动化性能数据不包含真实桌面渲染耗时；状态栏会单独显示这一阶段的持续耗时。
- 当前数据为单次 debug 样本。若建立性能门禁，应在固定硬件、release 构建和固定仓库快照上多次采样，并使用中位数与高分位数。
- 后续若继续优化首次大文件归因，建议新增可取消的块级任务队列，并对 patch inference 候选提交设置可观测的分段计时；该建议不在本阶段扩展实现。

## 7. 结论

分支项目快照、文件归因和提交下钻均已实现跨启动持久化恢复；不同分支独立保存且每分支只保留最近一次成功项目分析。手动项目刷新和当前文件刷新保持显式控制，失败不会清除可用缓存。统一状态栏覆盖所有主要载入阶段并保留本次耗时。
